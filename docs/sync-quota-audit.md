# 同步额度排查记录

记录日期：2026-09-20 至 2026-09-21。对应客户端版本：1.2.50。

本次问题的主要证据指向 **D1 每日读取额度耗尽**。数据存储总量较小，但旧查询和清理任务会反复扫描大量记录；增加设备数量会进一步放大这些读取。修复重点是减少扫描、控制每次请求的数据库查询数量，并让客户端按服务端提示延后重试。本次没有购买付费套餐或提高账单额度。

## 证据与结论的边界

下表区分生产观测和本地对比测试，不能将本地结果直接当作线上恢复证明。

| 来源与范围 | 结果 | 能说明什么 |
| --- | --- | --- |
| 2026-09-20 生产 D1 查询 | 数据库约 9.64 MB；`sync_records` 1,190 条；`sync_changes` 9,334 条 | 此时数据库规模并不接近免费单库容量上限。 |
| 近 7 天生产查询分析 | 旧清理语句出现 6 次，总读取 44,477,498 行，平均约 7,412,916 行/次 | 单次清理的读取量已经高于每日 500 万行额度；平均值经过舍入。 |
| 2026-09-20 生产 API 错误 | 返回代码 7500，并明确指出每日读取限额已耗尽 | 当时失败由读取额度阻断，不应误报为账号密码错误或本机空间不足。 |
| 本地 3,000 条记录、无新增变化的拉取对比 | 读取行数从 6,004 降至 4 | 新拉取路径避免在空闲轮询中扫描整份记录集。该数字对应测试中的拉取路径，不代表一整轮同步的所有请求。 |

依据是本次生产统计、实际错误响应及本地压测。数据库大小、记录数和历史查询数据是采样时的值，不是实时监控面板。

## 免费额度与计量方式

核对 Cloudflare 官方文档后，相关免费额度如下：

| 项目 | 免费额度 | 官方依据 |
| --- | --- | --- |
| D1 行读取 | 每日 5,000,000 行 | [D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/) |
| D1 行写入 | 每日 100,000 行 | [D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/) |
| D1 存储 | 单数据库 500 MB；账号合计 5 GB | [D1 Limits](https://developers.cloudflare.com/d1/platform/limits/) |
| 单次 Worker 调用中的 D1 查询 | 50 次 | [D1 Limits](https://developers.cloudflare.com/d1/platform/limits/) |
| Workers 请求 | 每日 100,000 次 | [Workers Limits](https://developers.cloudflare.com/workers/platform/limits/) |

D1 的“读取行数”包含查询扫描的行，不是只统计最终返回的行，也不是按数据库文件大小计算。因此，9.64 MB 的小数据库同样可能用完读取额度。每日读取、写入和请求限额也不等于每个 DeepStudy 用户各有一份额度；同一 Cloudflare 账号内的其他相关用量需要一并考虑。[D1 计量说明](https://developers.cloudflare.com/d1/platform/pricing/)、[Workers 每日请求限制](https://developers.cloudflare.com/workers/platform/limits/#daily-request)。

免费每日额度在 **00:00 UTC，即北京时间 08:00** 重置。对 2026-09-20 的读取耗尽事件，下一次预期重置时间是 **2026-09-21 08:00（北京时间）**。这是规则换算出的预期时间，不等于已经实测恢复；线上是否恢复仍应以重置后的实际请求为准。[D1 免费额度重置规则](https://developers.cloudflare.com/d1/platform/pricing/)。

## 本次实现调整

### 1. 拉取只处理游标之后的变化

`deepstudy-gateway/src/sync.ts` 先按账号与变化序号读取有界页面，再连接到实体当前记录，检查是否还有后续变化。空闲轮询不再为得到空结果而扫描账号全部记录。分页游标仍然保留，客户端会检测没有推进的异常游标。

### 2. 清理有索引、有游标、有上限

`deepstudy-gateway/src/cleanup.ts` 为实体变化顺序增加索引，使用 `maintenance_cursors` 保存清理进度，每页最多处理 1,000 条变化。即使整页记录都需要保留，游标也会推进，避免每次从头重复扫描。每个实体的最新变化仍被保留。

读取额度耗尽可能使迁移暂时无法执行。因此，清理入口还包含幂等的索引、游标表初始化：下一次清理能够访问 D1 时补齐这些结构。后续运行使用新的分页清理路径，以避免旧清理语句再次产生数百万行的重复扫描。首次建立索引仍有一次性成本，清理其他表也有额外读取，不能将其视为零成本。

2026-09-21 的生产查询统计已记录自动创建索引与分页清理执行；当天 14:05 左右又成功执行了幂等迁移 `0003_sync_query_costs.sql`，迁移账本已补齐。

### 3. 小批次上传符合单次查询预算

新客户端每批最多上传 5 条独立记录，并按序列化字节数控制请求大小。网关为兼容旧客户端，仍可接收最多 20 条的输入，但每次只确认一个安全前缀，未确认内容必须继续留在客户端队列。

限制到 5 条，是为每条记录涉及的幂等查询、版本读取、写入和冲突处理留出空间，同时预留会话验证等查询开销。它针对单次调用最多 50 次 D1 查询的约束；并没有增加每日 100,000 行写入额度，也不能把“一次批量请求”当作“一行写入”。

### 4. 自动同步与延后重试

桌面端在保存后安排同步，空闲时约 60 秒一轮，有活动后约 15 秒检查；保存发生在同步过程中时，会保留新修改并安排后续轮次。Android 保存后自动上传，前台约 60 秒检查，并在回到前台、恢复联网时唤醒。

网关将额度错误区分为 `SYNC_DAILY_READ_LIMIT`、`SYNC_DAILY_WRITE_LIMIT` 和 `SYNC_STORAGE_LIMIT`。每日额度错误返回 `retryAfterSeconds` / `Retry-After`，客户端保留待上传内容并据此安排重试，避免反复立即发送失败请求。云端空间不足提示管理员处理，不能通过等待每日重置来假定空间问题会消失。

### 5. 保留同步期间的新修改

桌面端在应用远端响应前重新采集已保存内容，将同步期间的新修改写入持久队列，暂缓覆盖有本机待上传内容的记录。Android 队列使用持久的单调顺序，确认旧上传时保留最新本机内容；若旧版本遗留队列乱序，最后确认的内容仍不是本机最新版本，会再排入一个新的修复操作。

同一条记录的并发修改仍可能进入冲突处理，不能将数据保护误解为自动判断哪个内容更正确。账号或服务切换时会检查作用域，避免把上一账号的在途结果写入下一账号。

## 三设备使用量估算

以下是代码优化后的场景估算，假设没有大规模历史回放、没有异常冲突积压，也没有其他服务的大量用量。实际值应读取 D1 `rows_read` / `rows_written` 与 Workers 请求统计。

| 场景 | 计算 | 读取量估算 |
| --- | --- | --- |
| 三台设备全天空闲在线，每台每分钟同步一次 | `3 × 1,440 = 4,320` 轮/日；按每轮约 10 行读取作近似预算 | 约 43,200 行/日；再加一页约 3,017 行的清理与少量额外查询，空闲基线可按低于 100,000 行/日留余量。 |
| 三台设备全天都按 15 秒检查 | `3 × 5,760 = 17,280` 轮/日 | 按同一假设约 172,800 行/日；为额外元数据查询与清理放大预算时，可用低于 1,000,000 行/日作为该场景的估算目标，而非保证。 |

第二行是对高频检查的压力假设；Android 的普通前台检查仍约每分钟一次。按每轮约 1–3 个 Worker 请求粗估，以上两种场景分别约 4,320–12,960 次和 17,280–51,840 次请求/日；真实路径、鉴权、重试和额外功能会改变数量。

因此，**正常三设备空闲或轻量编辑具备在免费额度内运行的空间**；之前动辄数百万行的清理扫描才是优先修复项。上述估算不包含所有工作负载：大量修改、图片分片、首次导入、长历史拉取、冲突处理、计时器心跳及同一 Cloudflare 账号的其他项目都会增加读取、写入和请求。计时器会使用独立请求，尤其不能拿普通任务的空闲估算代替持续计时用量。写入量取决于数据实际变化和索引维护，不能只用同步轮数推导。

## 仍然存在的大数据边界

日常同步分批与首次导入是两条不同路径。`deepstudy-gateway/src/imports.ts` 的首次预览仍限制本机记录数组最多 5,000 条、UTF-8 序列化大小最多 900,000 字节，读取的云端快照最多 5,000 条。`packages/sync-contract/index.js` 还限制单条 payload 为 256 KiB。

首次提交虽可分块继续，预览阶段的整份快照限制并未移除。超出限制的大型旧数据仍需要后续分页预览、导入方案；本次修复不能宣称“任意数据量都已支持”。处理前保留原始本机数据与备份，不建议通过删除或人为拆散记录来绕过校验。

## 恢复验证要求

额度重置后应先确认生产 API 可访问，再验证一轮小规模上传、读回以及空闲拉取，检查客户端待上传数据是否收敛。随后观察分页清理的实际读取行数和下一日额度曲线。健康检查成功不等于账号同步成功；本地测试通过也不等于生产限额已经恢复。
